# Wardley maps integration

Date: 2026-05-21
Status: Implemented (working tree, uncommitted)
Pinned wtg2svg version: commit `a31d299ed0100ace9c7ab9513a6b87b10bfc4ea3` (tag v2.30.2, published 2026-05-14)

## Context

The blog needs to render Wardley maps inside articles. Existing diagramming support (Mermaid, see `docs/article-formatting.md` §3) is unsuitable: Mermaid renders generic node graphs, not the Wardley canvas (evolution axis x value-chain axis with annotated movement).

The chosen renderer is [wardleyToGo](https://github.com/owulveryck/wardleyToGo) (`wtg2svg`), a Go CLI that reads a `.wtg2` DSL file from stdin and emits SVG to stdout.

**DSL note**: the renderer expects the **WTG2** grammar (file extension `.wtg2`), not the older WTG format. The repo-root `sample.wtg` is in the deprecated WTG syntax; the parser silently accepts it but produces an empty component layer. The correct example source is `wtg2/example.wtg2` in the upstream repo, and the system-installed `wtg2` Claude skill (at `~/.claude/skills/wtg2/SKILL.md`) generates valid WTG2 directly.

The integration must:

1. Fit the existing Hugo page-bundle convention (sidecar assets alongside `index.md`, already practiced for images and webp files).
2. Reuse the existing `layouts/_default/_markup/render-image.html` hook for free, including the `?zoom` lightbox (`docs/article-formatting.md` §5) and `<figcaption>` support.
3. Leave the GitHub Actions deploy workflow unchanged. Generated SVGs are committed to git; CI does not need `wtg2svg`.

## Approach

**Sidecar pattern.** Each article that contains a Wardley map gets a `.wtg2` source file in the page bundle, plus a generated `.svg` of the same basename in the same directory. The article references the `.svg` via standard Markdown image syntax. Both files are committed.

```
content/blog/<slug>/
  index.md          # ![Wardley map of X](map.svg "Caption")
  map.wtg2           # author-written DSL, diffable
  map.svg           # generated by `just wardley-render`, committed
```

A new justfile target `wardley-render` walks `content/**/*.wtg2`, invokes `wtg2svg < FILE > FILE.svg` for each, and is invoked **locally only** by the author after editing a `.wtg2` file. The production `build` target does NOT call `wardley-render`. The deploy pipeline serves the already-committed SVGs.

The existing `validate-images` step (justfile:411) is the safety net: any `index.md` that references a missing `.svg` fails the build, catching the case where an author commits a `.wtg2` change without re-rendering the SVG.

## Files

### Add

- **`scripts/wardley-render.sh`** walks `content/**/*.wtg2` using `find -print0` (resilient against filenames containing spaces, newlines, or leading dashes), runs `wtg2svg < "$f" > "${f%.wtg2}.svg"` for each, reports counts, fails on any non-zero exit. Pattern mirrors `scripts/optimize-images.sh` and `scripts/strip-exif.sh` already present in the repo.
- **Justfile target `wardley-render`** is a thin wrapper that invokes the script. Slotted into the Building group near `optimize-images` (justfile:403). Help line added in the Building section (justfile:58-69).

### Modify

- **`justfile` `init` target**: after the existing `harper-cli` install block (justfile:123-133), add an analogous block that runs `go install github.com/owulveryck/wardleyToGo/cmd/wtg2svg@a31d299ed0100ace9c7ab9513a6b87b10bfc4ea3` when `wtg2svg` is missing from PATH. `go` is already a hard prerequisite of `init` (justfile:89-93), so no new dependency is introduced. **Note**: the install target is a commit SHA, not the `@v2.30.2` tag. Upstream's `go.mod` declares the module path as `github.com/owulveryck/wardleyToGo` (without the `/v2` suffix that Go's semantic-import-versioning rule requires for major version >= 2), so any `@v2.x.x` tag install fails. The SHA form resolves to a v0.x.x pseudo-version (`v1.15.2-0.20260514123056-a31d299ed010`) and bypasses the SIV check. Bumping the pinned version is a deliberate two-step action: (1) look up the new tag's commit SHA on GitHub, (2) edit this line and the spec.
- **`justfile` `check` target**: add a `wtg2svg` availability check after the existing tool checks (around justfile:200). Make it fatal only when `find content -name '*.wtg2' -print -quit` returns a result, so machines without Wardley articles still build without the tool.
- **`docs/article-formatting.md`**: add a new section "Wardley maps" after Mermaid (between current §3 and §4). Document the sidecar pattern, the `.wtg2` DSL link to upstream docs, the `just wardley-render` workflow, the convention that `.wtg2` and `.svg` are committed together, and the option to append `?zoom` (which works for free via render-image.html).
- **`CLAUDE.md`**: under "Best practices", add: *"After editing any `.wtg2` file, run `just wardley-render` before committing, the generated `.svg` must travel with its source."* Add a Documentation Index pointer to the new article-formatting section.

### Plan deviation: render-image.html DID need modification

The pre-implementation plan listed `layouts/_default/_markup/render-image.html` as "do not modify," based on the assumption that Hugo would treat SVG resources identically to raster images. Empirical verification proved this false: Hugo's `Resource` API exposes `.Width` and `.Height` on **processable** image types (PNG, JPEG, WebP, GIF), but **not** on SVG. The existing template's `<img ... width="{{ $res.Width }}" ... >` call crashed at render time:

```
resource "map.svg" of media type "image/svg+xml" does not support this method
```

**Resolution (approved mid-implementation)**: an additive `{{ if hasSuffix $src ".svg" }}` branch inside the existing `{{ if $res }}` block. The SVG branch emits `<img>` without explicit `width`/`height` (the browser uses the SVG's intrinsic `viewBox`) and preserves the `?zoom` lightbox attributes. The raster branches are byte-identical to the pre-change template. Visual regression on raster images is zero.

### Do NOT modify

- **`build` target**: chaining `wardley-render` here would force CI to install `wtg2svg`, violating the "CI unchanged" decision.
- **`.github/workflows/hugo.yml`**: unchanged. Committed SVGs ship directly.

## Naming convention

- Single map per article: `map.wtg2` / `map.svg`.
- Multiple maps: descriptive basenames per map (e.g., `auth-evolution.wtg2`, `data-platform.wtg2`). The script handles arbitrary basenames; only the `.wtg2` extension is reserved.

## Security considerations

A threat model assessment (`threatmodel:quick`) was run against this plan. No critical risks. Findings incorporated:

1. **Supply chain (High, mitigated)**: `go install ...@latest` is replaced with a pinned tag or commit SHA in the `init` target. The pinned version is recorded in this spec when chosen during empirical verification step 1. Re-pinning is a deliberate, audited action.
2. **Filename robustness (Medium, mitigated)**: `scripts/wardley-render.sh` uses `find -print0 | while IFS= read -r -d '' f` rather than naive globbing.
3. **Parser-bug exposure (Medium, accepted)**: `wtg2svg` parses author-controlled DSL at build time on the author's machine. In a single-author blog this is equivalent to running any other developer tool; not mitigated.
4. **SVG script execution via direct URL (Low, accepted)**: generated SVGs are served as static assets and could in principle be loaded directly (`/blog/<slug>/map.svg`) where script tags would execute. `wtg2svg` is not known to emit scripted SVG, and the author is the only person writing `.wtg2` files. Sanitization (svgo/scour) is not added; revisit if the threat surface changes.
5. **Drift detection (Low, deferred)**: CI does not detect divergence between a modified `.wtg2` and its committed `.svg`. PR visual review and `just dev` preview are the controls. A future enhancement (hash comment + `validate-wardley` target) is documented as a deferred option.

## Verification

1. **Install (and pin)**: run `just init`. Confirm `wtg2svg --help` (or equivalent) succeeds. Record the resolved version/SHA in this spec and pin the `init` install command accordingly.
2. **Determinism gate**: create a minimal `test.wtg2` (syntax per upstream `examples/wtg2svg/`). Run `wtg2svg < test.wtg2 > a.svg && wtg2svg < test.wtg2 > b.svg && diff a.svg b.svg`. **If the diff is non-empty, the renderer is non-deterministic** and every author save will produce spurious git churn. Mitigation if it fails: post-process the SVG to strip the offending timestamp or randomized ID. Do not proceed past this gate.
3. **Test bundle**: create `content/blog/test-wardley/` with `draft: true`, `index.md` containing `![Test](map.svg)`, and a working `map.wtg2`.
4. **Render**: `just wardley-render`. Confirm `map.svg` is produced and is valid SVG (`file map.svg` reports SVG; `xmllint --noout map.svg` parses).
5. **Live render**: with `just dev` running, visit the test page. Confirm the SVG renders inside the existing `<figure>`. Confirm caption appears when the image syntax has a title.
6. **Zoom path**: change the markdown to `![Test](map.svg?zoom "...")`. Confirm the lightbox opens at full resolution.
7. **Backstop**: delete `map.svg` and run `just validate-images`. Confirm it fails with the missing-file error.
8. **End-to-end**: run `just build`. Confirm green.
9. **Cleanup**: delete the test bundle before merging the feature.

## Risks

- **Non-determinism** (gated by Verification step 2): the highest-probability blocker. If `wtg2svg` embeds wall-clock timestamps or random element IDs, the sidecar-plus-commit strategy generates a diff on every author save. Mitigation is a post-render `sed` filter; full mitigation may require a small Go wrapper. Discover early.
- **Author discipline** for the `.wtg2` to `.svg` pairing is required but partially enforced by `validate-images` against the markdown reference. Content drift (author edits `.wtg2`, forgets to re-render) is not caught by CI under the chosen architecture. Acceptable for a single-author blog: PR visual review and local `just dev` preview catch it.
